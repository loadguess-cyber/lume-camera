# 테스트 현황과 개선 제안

이 저장소에는 **자동화된 테스트가 하나도 없습니다.** 이 문서는 지금 상태를
정리하고, 어디부터 테스트를 붙이면 값이 가장 큰지를 순서대로 제안합니다.

---

## 1. 지금 상태

| 항목 | 상태 |
|---|---|
| 테스트 파일 | 0개 |
| 테스트 러너 (jest·vitest·node:test 등) | 없음 |
| `package.json` 의 `test` 스크립트 | 없음 |
| CI 의 테스트 단계 | 없음 (`android.yml` 은 APK 빌드만, `pages.yml` 은 배포만) |
| 린터·포매터 | 없음 |
| 커버리지 측정 | 없음 |

측정 대상 코드는 대략 4,900줄(`www/js/` 4,428줄 + `scripts/` 467줄)이고,
**줄 커버리지는 0%** 입니다.

지금 회귀를 잡아주는 장치는 `scripts/render-presets.js` 하나뿐인데,
이것은 결과 PNG 를 사람이 눈으로 보는 도구이지 통과/실패를 판정하지
않습니다. 즉 "프리셋 색이 예전과 달라졌다"를 아무도 자동으로 못 잡습니다.

### 왜 이게 지금 문제인가

`www/js/` 의 모듈들은 전역(`window.XMP`, `window.GL` …)에 붙는 IIFE 라서
서로 강하게 묶여 있고, 색 파이프라인은 값이 조금만 틀어져도 결과가
"틀렸다"기보다 "미묘하게 다르다"로 나타납니다. 사람 눈으로는 회귀를
놓치기 쉬운 종류의 코드이므로, 숫자로 고정해 두는 이득이 특히 큽니다.

## 2. 무엇부터 테스트할지 — 3단계로 나눕니다

코드를 **테스트 난이도**와 **깨졌을 때의 피해**로 나누면 이렇게 됩니다.

| 계층 | 파일 | 브라우저 필요? | 우선순위 |
|---|---|---|---|
| 순수 로직 | `xmp.js`, `zip.js`, `analyze.js`(계산부), `gl.js`(LUT·스플라인), `camera.js`(`fitRect` 등) | 아니오 | **높음** |
| 브라우저 API 의존 | `store.js`, `sample.js`, `analyze.js`(캔버스부), `gl.js`(렌더러) | jsdom / headless Chromium | 중간 |
| 화면·기기 의존 | `ui.js`, `studio.js`, `camera.js`(스트림·녹화), `app.js` | 실기기 또는 Playwright | 낮음 |

**순수 로직부터 하는 것이 맞습니다.** 브라우저 없이 돌고, 가장 많이 재사용되며
(`xmp.js` 는 `gl.js`·`ui.js`·`studio.js`·`render-presets.js` 가 모두 씁니다),
아래에서 보듯 실제로 이미 버그가 들어 있습니다.

## 3. 우선순위별 제안

### 영역 1 — `xmp.js` 프리셋 데이터 모델 (최우선)

`normalize()` 는 저장된 프리셋, 가져온 XMP, 내장 프리셋이 **모두 통과하는
단 하나의 관문**입니다. 여기가 틀리면 나머지 전부가 틀립니다.

실제로 확인된 결함 두 가지:

**(가) `normalize()` 가 인자의 커브 배열을 복사하지 않고 참조로 가져갑니다**
([`xmp.js:72`](../www/js/xmp.js#L72))

```js
const input = { curve: { rgb: [[0,0],[128,140],[255,255]] } };
const out = XMP.normalize(input);
out.curve.rgb[1][1] = 999;
// input.curve.rgb === [[0,0],[128,999],[255,255]]  ← 호출자의 객체가 바뀝니다
```

`presets.js:176` 이 내장 프리셋을 `normalize()` 한 결과를
`BUILTIN_PRESETS` 로 내보내고, `gl.js:405` 의 `setPreset()` 이 그것을 다시
`normalize()` 하므로, **렌더러의 `this.preset.curve` 는 내장 프리셋과 같은
배열입니다.** 지금은 아무도 렌더러의 프리셋을 직접 고치지 않아 드러나지
않지만, 커브를 실시간으로 만지는 기능을 하나 붙이는 순간 내장 프리셋 9종이
전역에서 오염됩니다. `ui.js` 는 호출 지점마다 `JSON.parse(JSON.stringify())`
로 방어하고 있는데(`ui.js:440`, `485`, `492`, `843`), 그 방어를 잊은 곳이
바로 `gl.js:405` 입니다.

**(나) `Infinity` 가 HSL 값으로 통과합니다** ([`xmp.js:80`](../www/js/xmp.js#L80))

```js
XMP.normalize({ hsl: { sat: [ '10','x',null,undefined,NaN,Infinity,-0,'' ] } })
// → sat: [10, 0, 0, 0, 0, Infinity, 0, 0]
```

`+v || 0` 은 `NaN`·`null`·`''` 는 걸러내지만 `Infinity` 는 truthy 라 그대로
통과합니다. 이 값은 `gl.js:420` 에서 `/100` 되어 셰이더 유니폼으로 들어가고
화면 전체가 깨집니다. 손상된 `localStorage` 나 남이 만든 프리셋 JSON 이면
충분히 도달할 수 있는 경로입니다.

제안하는 테스트:

- `normalize()` 는 인자를 **읽기만** 한다 — 호출 전후로 인자를 깊은 비교
- `normalize()` 의 결과는 인자와 배열을 공유하지 않는다
- `normalize(normalize(x))` 는 `normalize(x)` 와 같다 (멱등)
- 값이 빠진 것 / 타입이 틀린 것 / `NaN`·`Infinity`·`-0`·문자열 숫자 /
  8개보다 짧거나 긴 HSL 배열 / 2점 미만 커브 — 전부 유한한 기본값으로 수렴
- `neutral()` 을 두 번 부르면 서로 다른 객체다 (공유 상태 없음)
- 내장 프리셋 9종 전부가 `normalize()` 후 스키마를 만족한다
- `isNeutral()` 은 정규화되지 않은 객체(`{}`)에 대해 `false` 를 준다 —
  현재 동작이며, 의도라면 문서화하고 아니면 내부에서 `normalize()` 해야 합니다

### 영역 2 — XMP 왕복 (parse ↔ serialize)

"라이트룸에서 그대로 열린다"가 README 가 내세우는 기능인데, 이걸 지켜주는
장치가 없습니다. `serialize()` 는 자체 검증이 되지만 `parse()` 는
`DOMParser` 가 필요하므로 jsdom 또는 headless Chromium 이 있어야 합니다.

`serialize()` 만으로 확인한 **정밀도 손실** (모두 의도된 것으로 보이나,
어디까지 손실을 허용하는지가 어디에도 적혀 있지 않습니다):

| 입력 | 기록되는 값 | 다시 읽으면 |
|---|---|---|
| `temp: 12.6` | `+13` | `13` |
| `tint: -3.4` | `-3` | `-3` |
| `exposure: 0.125` | `+0.13` | `0.13` |
| `sharpen: 37` | `Sharpness="56"` | `56/150*100 = 36.67` |

제안하는 테스트:

- 내장 프리셋 9종에 대해 `parse(serialize(p))` ≈ `p` — 항목별 허용 오차를
  명시적으로 못박기 (정수 항목 ±0.5, 노출 ±0.005, 선명도 ±0.7)
- 왕복을 두 번 해도 값이 더 이상 움직이지 않는다 (`parse∘serialize` 가 멱등)
- 실제 라이트룸 `.xmp` 픽스처 몇 개를 `test/fixtures/` 에 넣고 파싱:
  속성형(`crs:Exposure2012="…"`)과 요소형(`<crs:Exposure2012>…`) 양쪽,
  구형 키(`Exposure`/`Clarity`/`FillLight`)만 있는 파일, `ToneCurve` 만 있고
  `ToneCurvePV2012` 는 없는 파일
- 절대 색온도만 있는 파일 → `kelvinToRel()` 경로 (2000K·5500K·9000K 에서
  ±100 밖으로 안 나가는지)
- 깨진 XML → `'XMP 형식을 읽을 수 없습니다'` 로 throw 하고, 빈 파일·
  `crs:` 가 하나도 없는 XML 은 중립 프리셋으로 떨어진다
- 프리셋 이름의 XML 이스케이프: `&`, `<`, `>`, `"` 는 처리되지만
  `'` 는 그대로 나갑니다 — 속성이 아니라 요소 텍스트라 유효하나,
  왕복으로 확인해 둘 값어치가 있습니다
- `lume:Fade` 가 왕복을 견디는지 (라이트룸이 무시하는 자체 네임스페이스)

### 영역 3 — `zip.js` 일괄 내보내기 (확인된 버그 있음)

Studio 의 일괄 내보내기 결과물 전체가 이 140줄에 달려 있고,
바이트를 직접 조립하기 때문에 틀려도 조용히 틀립니다.
`crc32()` 는 표준 벡터(`"123456789"` → `0xCBF43926`)를 정확히 통과했지만,
**파일명 중복 처리는 깨져 있습니다** ([`zip.js:127-133`](../www/js/zip.js#L127)):

```js
Zip.fromBlobs([
  { name: 'a.jpg', … }, { name: 'a.jpg', … },
  { name: 'a.jpg', … }, { name: 'a_2.jpg', … },
]);
// → ["a.jpg", "a_2.jpg", "a_3.jpg", "a_2.jpg"]   ← a_2.jpg 가 둘
```

중복을 피하려고 붙인 접미사가 **이미 그 이름을 가진 파일과 다시 충돌**합니다.
결과 ZIP 에 같은 이름이 두 개 들어가고, 푸는 도구에 따라 한 장이 조용히
사라집니다. 카메라롤에서 `사진.jpg`, `사진_2.jpg` 를 같이 고르면 바로 걸리는,
충분히 흔한 경우입니다.

MS-DOS 날짜 필드도 범위 밖에서 넘칩니다:

| 촬영 연도 | 기록되는 필드 |
|---|---|
| 1979 | `0xFE21` (쓰레기값) |
| 1980 | `0x0021` |
| 2026 | `0x5C21` |
| 2108 | `0x0021` ← 1980 으로 되돌아감 |

기기 시계가 틀어져 있으면 도달합니다. 크래시는 아니고 압축 파일의 날짜만
이상해지므로 우선순위는 낮지만, 테스트로 고정해 둘 값어치는 있습니다.

제안하는 테스트:

- `crc32()` 표준 벡터 + 빈 입력 + 1MB 입력
- `build()` 결과를 다시 파싱: 로컬 헤더 시그니처, 중앙 디렉터리 오프셋,
  EOCD 의 항목 수, 각 항목의 크기·CRC 가 실제 데이터와 맞는지
- 한글 파일명이 UTF-8 **바이트 길이**로 기록되고 플래그 `0x0800` 이 켜지는지
  (현재 올바릅니다 — 회귀 방지용으로 고정)
- 빈 파일 목록 → 22바이트 EOCD 만 (현재 올바름)
- **중복 이름: 위 케이스가 서로 다른 이름 4개를 내야 합니다** (지금은 실패)
- 0바이트 파일이 섞인 경우
- 가능하면 `unzip -t` 나 순수 JS 압축 해제기로 결과물을 교차 검증

### 영역 4 — `gl.js` 의 CPU 쪽 (커브 LUT)

셰이더는 GPU 없이 테스트하기 어렵지만, `monotoneSpline()` ·
`parametricDelta()` · `buildCurveLUT()` · `isIdentityCurve()` ·
`gradeOffset()` 는 전부 순수 함수이고 프리셋의 색을 실제로 결정합니다.
`buildCurveLUT(neutral())` 이 항등 LUT(최대 오차 0)를 내는 것은 확인했습니다.

`monotoneSpline()` 의 확인된 사각지대:

```js
GL.monotoneSpline([[255,255],[0,0]])(128)  // → 255  (정렬 안 된 입력에서 조용히 오답)
GL.monotoneSpline([[0,0]])(128)            // → 0    (점 1개면 전부 0)
```

이분 탐색이 x 오름차순을 전제하는데, `normalize()` 는 정렬해주지 않습니다.
`XMP.points()` 는 정렬하므로 XMP 경로는 안전하지만, `localStorage` 나
손으로 만든 프리셋 JSON 은 그대로 들어옵니다.

제안하는 테스트:

- 항등 커브 → 항등 LUT (오차 0) — 이미 성립, 고정할 것
- **단조성**: 입력 점이 단조 증가면 LUT 256칸도 단조 증가 (Fritsch–Carlson
  이 보장해야 하는 성질이자, 계조가 뒤집히지 않음을 뜻함)
- 오버슈트 없음: 모든 출력이 0~255 안 (`Math.min/max` 로 잘리므로 클램프
  **이전** 값을 봐야 의미가 있습니다)
- 정렬 안 된 입력 / 점 1개 / x 가 겹치는 점 / 점 20개 — 던지거나
  방어하거나, 어느 쪽이든 정해서 고정
- `parametricDelta()`: 네 값이 모두 0이면 정확히 0; 부호가 맞는 방향으로
  움직이는지; split 이 뒤집힌 경우(`splitSh > splitHi`)도 유한한 값
- `isIdentityCurve()` 가 `true` 인 프리셋은 `buildCurveLUT()` 도 항등이어야
  한다 (둘이 어긋나면 커브가 조용히 무시됩니다)
- `gradeOffset()`: 채도 0 이면 `[0,0,0]`; 색상각 0·360·-40·400 이 같은 결과;
  결과의 휘도 성분이 0에 가까움 (휘도가 제거된 색 오프셋이라는 주석의 계약)
- **골든 테스트**: 내장 프리셋 9종의 LUT 1024바이트를 스냅샷으로 저장.
  `parametricDelta()` 의 상수를 건드리면 바로 드러납니다.

### 영역 5 — `analyze.js` 자동 화이트밸런스

`awbGains()` 는 순수 함수(`Uint8ClampedArray` → 게인 3개)라 픽셀 배열만
만들어 주면 브라우저 없이 전부 테스트됩니다. 지금 동작:

| 입력 프레임 | 결과 |
|---|---|
| 무채색 128,128,128 | `[1, 1, 1]` |
| 텅스텐 200,150,100 | `[0.556, 1, 1.8]` ← 파랑이 상한에 딱 붙음 |
| 전부 어두움 10,10,10 | `null` (판단 보류) |
| 전부 날아감 250,250,250 | `null` |
| 유효 화소 100개 | `null` (`MIN_PIXELS` 120) |

제안하는 테스트:

- 무채색 프레임 → `[1,1,1]` (오차 1e-6)
- 게인이 절대 `[1/1.8, 1.8]` 밖으로 안 나간다 — 극단적인 단색 프레임으로
  `MAX_GAIN` 경계를 정확히 때리기 (텅스텐 케이스가 이미 상한에 붙어 있어,
  상수를 조금만 바꿔도 결과가 달라집니다)
- `null` 을 돌려주는 세 경우: 유효 화소 부족, 전부 `mn < 16`, 전부 `mx > 246`
- 잘라먹기 임계값 경계: 정확히 16 과 246 인 화소가 포함되는지 제외되는지
- `smooth()`: `prev` 가 `null` 이면 `next` 의 **복사본** (호출자 배열을
  공유하지 않을 것), `k=0` 이면 `prev` 유지, `k=1` 이면 `next`,
  반복 호출이 `next` 로 수렴
- `gainsToLabel()` 의 세 구간 경계 (1.06 · 0.94) 양쪽
- `histogram()`: 256칸 합 = 화소 수, 단색 프레임은 한 칸에 몰림,
  휘도 계수(0.2126/0.7152/0.0722) 확인
- `clipping()`: 완전 검정 프레임 → `low = 1`, 완전 흰색 → `high = 1`

### 영역 6 — `camera.js` 의 순수 계산부

카메라 스트림 자체는 실기기 문제지만, **어떤 크기로 잘라 저장할지**를
정하는 계산은 순수 함수이고 화질에 직결됩니다. `fitRect()` 는 커밋
`4304b1c`("늘려 찍던 것을 멈추고") 에서 고쳐진 함수인데, **그 수정을
지켜주는 테스트가 없습니다.** 지금이라도 붙여야 할 대표적인 자리입니다.

제안하는 테스트:

- `fitRect()` 의 결과는 **항상 원본 안에 들어간다** (다시 늘려 찍지 않음) —
  이것이 위 커밋이 고친 바로 그 성질
- 결과 비율이 목표 비율과 ±0.5% 안
- 폭·높이가 항상 짝수 (인코더 요구사항)
- 가로 소스 / 세로 소스 / 정사각 소스 × `3:4`·`9:16`·`1:1` 조합
- **아주 작은 소스에서 성질이 깨집니다**: `fitRect(1, 1, 3/4)` 는 `2×2` 를
  돌려주어 원본보다 큽니다. 최소 크기 2 를 보장하는 절이 "늘리지 않는다"는
  약속과 충돌합니다. 실사용에서 1×1 프레임은 안 나오므로 피해는 없지만,
  테스트를 쓰면 바로 드러나는 자리라 규칙을 정해둘 값어치가 있습니다
- `ratioValue()`: 알 수 없는 문자열은 `3:4` 로 (현재 동작)
- `extFor()` / `extForImage()`: mp4·webm·빈 문자열·`undefined`
- `qualityStep()`: 알 수 없는 `photoQuality` 는 `high` 로
- `pickMime()`: `MediaRecorder.isTypeSupported` 를 가짜로 물려 우선순위 확인
  (mp4 를 webm 보다 먼저 고르는지), 지원 형식이 없으면 `''`,
  `MediaRecorder` 가 아예 없으면 `null`

### 영역 7 — `store.js` 저장소 (jsdom 필요)

작지만 모든 지속 상태가 여기를 지납니다.

- `read()` 가 손상된 JSON / 빈 문자열 / `localStorage` 접근 자체가 던지는
  경우(사파리 프라이빗)에 조용히 기본값으로 떨어지는지
- `write()` 가 용량 초과에서 `false` 를 돌려주고 던지지 않는지
- 저장된 설정에 모르는 키가 있어도 `DEFAULT_SETTINGS` 와 합쳐지는지,
  그리고 **모르는 키가 살아남는지 버려지는지** (현재 살아남습니다)
- `stamp()` 의 자리수 채움 — 한 자리 월·일·시에서
- `clamp()` 의 경계 · `min > max` 인 경우
- `uid()` 가 대량 호출에서 겹치지 않는지
- `saveFile()` 의 두 갈래: 웹은 `<a download>`, 네이티브는
  Filesystem → Share. **공유창을 닫아도 `{ ok: true }` 여야 한다** —
  주석에 적힌 계약인데 회귀하기 쉬운 종류입니다
  ([`store.js:111-120`](../www/js/store.js#L111))

### 영역 8 — 그 다음 (화면 · 통합)

`ui.js`(1,528줄)와 `studio.js`(551줄)는 DOM 과 뒤엉켜 있어 지금 구조로는
단위 테스트가 어렵습니다. 여기는 단위 테스트를 억지로 넣기보다
**Playwright 로 흐름 몇 개를 확인**하는 편이 값이 큽니다
(`render-presets.js` 가 이미 headless Chromium 을 쓰고 있어, 같은 도구를
그대로 재사용할 수 있습니다):

- `try.html` 을 열고 샘플 장면에 프리셋 9종을 적용 → 캔버스 픽셀을 스냅샷과
  비교 (셰이더 전체를 한 번에 덮는 유일한 방법)
- Studio: 사진 3장 넣기 → 프리셋 지정 → 내보내기 → 받은 ZIP 이 열리고
  JPEG 3장이 들어 있는지
- 프리셋 만들기 → `.xmp` 내보내기 → 그 파일을 다시 가져오기 → 값이 같은지
- WebGL 이 없는 환경에서 `index.html` 이 에러 화면을 보여주고 죽지 않는지

`ui.js` 안에서도 `fmtShutter()`(1122), `hsvToRgb()`(757), `hsvCss()`(753) 은
DOM 도 모듈 상태도 건드리지 않는 순수 함수라, 따로 빼내면 바로 테스트할 수
있습니다 — DOM 을 걷어내는 리팩터링의 자연스러운 첫걸음입니다.

## 4. 어떻게 붙일지

지금 구조에서 가장 마찰이 적은 방법:

1. **러너**: Node 내장 `node:test` — 의존성이 하나도 안 늘고,
   커버리지도 `node --test --experimental-test-coverage` 로 바로 나옵니다.
   `www/js/*.js` 는 IIFE 라 `require()` 가 안 되므로, 테스트에서
   파일을 읽어 `vm` 컨텍스트에 넣는 얇은 로더 하나면 충분합니다
   (`render-presets.js:71` 이 이미 같은 일을 브라우저에서 하고 있습니다).
   나중에 각 파일 끝에 `if (typeof module !== 'undefined') module.exports = …`
   두 줄을 더하면 로더도 필요 없어집니다 — 브라우저 동작에는 영향이 없습니다.
2. **DOM 이 필요한 것**(`DOMParser`, `localStorage`): `jsdom` 을 devDependency
   로. 영역 2·7 에만 필요합니다.
3. **픽셀·WebGL**: 이미 있는 Playwright 경로를 재사용.
4. **CI**: `.github/workflows/` 에 `npm test` 를 도는 워크플로 하나.
   빠른 순수 로직 테스트는 모든 푸시에서, Playwright 스냅샷은 `main` 에서만.

`package.json` 에 필요한 것:

```json
"scripts": {
  "test": "node --test test/",
  "test:coverage": "node --test --experimental-test-coverage test/"
}
```

## 5. 목표

순서대로 잡으면 이렇게 됩니다.

| 단계 | 범위 | 예상 커버리지 | 얻는 것 |
|---|---|---|---|
| 1 | 영역 1·3 (`xmp.normalize`, `zip`) | ~15% | 확인된 버그 3개를 잡고 회귀 방지 |
| 2 | 영역 4·5·6 (LUT · AWB · fitRect) | ~35% | 색 파이프라인과 화질이 숫자로 고정됨 |
| 3 | 영역 2·7 (jsdom: XMP 왕복 · 저장소) | ~55% | "라이트룸에서 열린다"가 검증됨 |
| 4 | 영역 8 (Playwright) | — | 셰이더와 주요 흐름이 덮임 |

`www/js/` 의 순수 로직 부분에 대해서는 **80% 이상**이 현실적인 목표이고,
`ui.js`·`studio.js` 를 포함한 전체로는 리팩터링 없이 55~60% 가 상한입니다.
